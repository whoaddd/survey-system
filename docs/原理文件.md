# 问卷系统原理介绍

本文档说明系统的整体架构、模块职责、关键设计决策，用于快速理解系统的运作机制与设计意图。

---

## 一、设计原则

系统在设计时遵循以下四条原则：

| 原则                               | 说明                                                         |
| ---------------------------------- | ------------------------------------------------------------ |
| **先定不做什么**                   | 首版明确不做：逻辑跳转、协作编辑、多租户、答卷者账号体系     |
| **按失败模式拆分**                 | 拆微服务的依据是"故障会不会互相拖累"，而不是"数据库里有没有这张表" |
| **高代价决策前置**                 | 数据模型、接口契约、版本矩阵在项目早期定死                   |
| **每个设计决策都要有失败场景撑着** | 撑不住的复杂度一律砍掉                                       |

其中"按失败模式拆分"是微服务拆分的核心依据：

- **AI 会超时、失败、限流** → AI 必须独立成服务，不能拖垮问卷 CRUD
- **附件上传是大流量、占内存** → 文件服务独立，二进制不进业务服务
- **题目/选项与问卷是整体-部分关系** → **不拆**，否则引入分布式一致性复杂度

## 二、整体架构

### 2.1 分层视图

```
┌──────────────────────────────────────────────────┐
│ 接入层                                            │
│   web (Nginx) :80  ──  静态资源 + /api 反代       │
│   gateway :8000    ──  JWT + 白名单 + 路由        │
├──────────────────────────────────────────────────┤
│ 业务服务层                                        │
│   user-service     :9001  用户/注册/登录/JWT      │
│   survey-service   :9002  问卷 CRUD/发布/快照     │
│   response-service :9003  答卷提交/防重/统计      │
│   file-service     :9005  MinIO 预签名/元数据     │
├──────────────────────────────────────────────────┤
│ AI 编排层                                         │
│   ai-orchestrator  :9004  AI 生成/评分/审计       │
├──────────────────────────────────────────────────┤
│ 基础设施层                                        │
│   MySQL / Redis / MinIO / Nacos                  │
└──────────────────────────────────────────────────┘
```

### 2.2 为什么是这套划分

| 服务                 | 拆分的依据                           | 如果合并会怎样                                      |
| -------------------- | ------------------------------------ | --------------------------------------------------- |
| **gateway**          | 所有请求的统一入口                   | 每个服务都要实现 JWT 校验，重复代码多；限流无法集中 |
| **user-service**     | 被所有服务依赖的基础能力             | 用户数据分散在多个服务，无法统一管理                |
| **survey-service**   | 问卷聚合根（题目、选项是聚合内实体） | 如果拆"题目服务"，问卷和题目之间要跨服务事务        |
| **response-service** | 高写入、只读、需防重                 | 与问卷 CRUD 混在一起，提交高峰会拖慢编辑            |
| **file-service**     | 大流量、二进制、直传 MinIO           | 二进制经过业务服务内存，JVM OOM 风险                |
| **ai-orchestrator**  | 外部依赖（模型 API）会超时/限流      | AI 挂了问卷也编辑不了，故障扩散                     |

## 三、模块详解

### 3.1 接入层

#### 3.1.1 `web`（Nginx + 前端静态资源）

**作用**：

- 托管 Vue 3 打包后的静态资源
- `/api/**` 请求反向代理到 gateway:8000
- History 模式路由回退（`try_files $uri $uri/ /index.html`）
- 静态资源缓存（7 天）

**为什么用 Nginx**：

- 静态资源访问远快于 Node.js 或 Java
- 生产环境只暴露 80 端口，内部服务不直接对外
- 与 gateway 形成"接入层双保险"——外网无法直接访问微服务

**关键设计**：

- **单前端工程双路由**：`/admin/**`（发布端）和 `/s/**`（答卷端）在同一个 Vue 工程里，靠路由守卫区分
- 不拆两个工程的理由：发布端和答卷端共享类型定义、API 封装、组件（QuestionRenderer），拆开会导致大量重复

#### 3.1.2 `gateway`（API 网关）

**作用**：

- **路由转发**：按 `Path` 规则把请求分发到 6 个后端服务
- **JWT 校验**：全局过滤器 `AuthGlobalFilter` 校验 token
- **白名单放行**：`/api/auth/login`、`/api/auth/register`、`/api/public/**`、`/api/file/url`
- **统一 401 响应**：返回 JSON 格式 `{code:40101, message:"未登录"}`，前端统一跳登录页

**核心技术**：

| 组件                                | 作用                               |
| ----------------------------------- | ---------------------------------- |
| `spring-cloud-starter-gateway`      | 基于 WebFlux 的响应式网关          |
| `spring-cloud-starter-loadbalancer` | 从 Nacos 拉取实例做负载均衡        |
| `AuthGlobalFilter`                  | 全局过滤器，order=-1（最高优先级） |

**关键设计：路由顺序**

Gateway 的路由匹配是**线性顺序**，第一个命中的就用它。**具体路径必须放在通用路径之前**：

```yaml
routes:
  # ✅ 具体路径在前
  - id: survey-results
    predicates:
      - Path=/api/surveys/*/responses,/api/surveys/*/statistics
  # ✅ 通用路径在后
  - id: survey-crud
    predicates:
      - Path=/api/surveys/**
```

**反例**：如果 `/api/surveys/**` 在 `survey-results` 前面，`GET /api/surveys/7/statistics` 会被转发到 survey-service，返回 404——因为 survey-service 根本没有 `/statistics` 接口。

**关键设计：双层鉴权放行**

公开接口必须**两层都放行**：

| 层      | 位置                            | 作用                                 |
| ------- | ------------------------------- | ------------------------------------ |
| Gateway | `AuthGlobalFilter.WHITE_LIST`   | 第一道门，决定请求能不能进           |
| 服务层  | `WebConfig.excludePathPatterns` | 第二道门，决定服务内部拦截器是否跳过 |

**只改一层会报 401**——Gateway 放行了，但请求到服务后被 `JwtInterceptor` 拦下，返回 401。

### 3.2 业务服务层

#### 3.2.1 `user-service`（用户服务）

**作用**：

- 账号注册（开放注册，无验证）
- 账号登录（BCrypt 密码校验）
- JWT 签发（包含 `userId`、`username`、`role`）
- JWT 解析拦截器（供其他服务复用）

**数据库**：`user_db.user`

| 字段            | 说明                  |
| --------------- | --------------------- |
| `username`      | 登录名，唯一索引      |
| `password_hash` | BCrypt 哈希（自带盐） |
| `role`          | `PUBLISHER` / `ADMIN` |
| `status`        | `1` 启用 / `0` 禁用   |

**关键设计**：

| 决策                              | 理由                                                         |
| --------------------------------- | ------------------------------------------------------------ |
| BCrypt 而非 MD5/SHA               | 自带随机盐，抗彩虹表；慢哈希，抗暴力破解                     |
| 注册即返回 token                  | 注册成功后直接登录，减少一次请求                             |
| `spring-security-crypto` 独立引入 | 只取 BCrypt 能力，不引入 Security 过滤器链，避免与现有配置冲突 |
| 拦截器复制到每个服务              | 不抽 common，因为 common 不能引 servlet 依赖（会拖垮 Gateway） |

**JWT 拦截器**：

```java
public boolean preHandle(...) {
    String header = request.getHeader("Authorization");
    if (header == null || !header.startsWith("Bearer ")) {
        response.setStatus(401); return false;
    }
    try {
        Claims claims = jwtUtil.parse(header.substring(7));
        request.setAttribute("userId", Long.valueOf(claims.getSubject()));
    } catch (Exception e) {
        response.setStatus(401); return false;
    }
    return true;
}
```

**关键**：`request.setAttribute("userId", ...)` 是下游 Controller `@RequestAttribute("userId")` 的数据来源。

#### 3.2.2 `survey-service`（问卷服务）

**作用**：

- 问卷 CRUD（创建、列表、详情）
- 草稿保存（**整体覆盖式**）
- 问卷发布（生成分享码、冻结版本）
- 关闭、复制为新草稿、删除
- 富文本 HTML 净化（Jsoup）

**数据库**：`survey_db.survey`、`survey_db.question`、`survey_db.question_option`

**核心：快照机制**

| 字段                       | 作用               |
| -------------------------- | ------------------ |
| `survey.version`           | 当前编辑版本号     |
| `survey.published_version` | 发布时冻结的版本号 |

**发布时的动作**：

```java
survey.setPublishedVersion(survey.getVersion());  // 冻结
survey.setStatus("PUBLISHED");
survey.setShareCode(generateShareCode());         // 8 位 base62
```

**为什么需要快照**：

假设发布者发布问卷（v1），答卷者 A 打开开始答题，此时发布者修改了题目（v2）并保存。如果没有快照，A 提交时会对不上题目，答卷数据错乱。

快照机制保证：**答卷者始终看到发布时的题目**，发布者的后续编辑基于新 version（v2），两者互不影响。

**核心：整体覆盖式保存**

草稿保存的实现：

```
1. 全量校验题目列表
2. 删除当前 version 下的所有 question 和 question_option
3. 按提交顺序重建 question 和 question_option
4. sortOrder 由服务端 1..N 赋值
```

**为什么整体覆盖而非增量更新**：

- 增量更新需要处理"删题、改题、加题、排序"的交叉情况，逻辑复杂度高
- 整体覆盖语义简单：前端提交什么，数据库就是什么
- 校验失败时事务回滚，数据不变

**代价**：`question.id` 每次重建都变化。S4 接入附件时，`attachment_ref.biz_id` 会失效——**这是已知问题，通过 `object_key` 追踪而非 `biz_id` 缓解**。

**核心：发布后不可编辑**

```java
if (!"DRAFT".equals(survey.getStatus())) {
    throw new BusinessException(..., "已发布问卷不可直接编辑，请复制为新草稿");
}
```

**复制为新草稿**的逻辑：

- 新建 `survey`（`version = 原 publishedVersion + 1`，`status=DRAFT`）
- 复制 `published_version` 的题目和选项到新 version
- 新问卷没有 `shareCode`，发布时才生成

**为什么用复制而非原地改 version**：

原问卷的 `shareCode` 已对外发布，答卷者可能正在填写。原地改 version 会让**同一链接在不同时间对应不同题目**，破坏答卷一致性。

**核心：富文本 HTML 净化**

使用 Jsoup 白名单过滤：

```java
Safelist.basicWithImages()
    .addTags("p", "br", "span", "h1", "h2", "h3")
    .addAttributes("img", "src", "alt", "width", "height")
    .addAttributes("span", "style")
```

**为什么服务端净化**：前端净化可绕过（改 DOM、改请求）。服务端是最后防线。

#### 3.2.3 `response-service`（答卷服务）

**作用**：

- 公开问卷读取（`GET /api/public/surveys/{shareCode}`）
- 答卷提交（`POST /api/public/responses`）
- 匿名防重（`respondent_key` + 唯一索引）
- IP 限流（Redis）
- 结果统计（答卷列表 + 统计聚合）

**数据库**：`response_db.response`、`response_db.response_answer`，**只读** `survey_db`

**核心：双数据源**

`response-service` 需要同时访问：

- `survey_db`（读题目、选项）
- `response_db`（写答卷、读统计）

使用 `dynamic-datasource-spring-boot3-starter`，在 Mapper 接口上标注 `@DS`：

```java
@DS("survey")
public interface SurveyRefMapper extends BaseMapper<SurveyRef> {}

@DS("response")
public interface ResponseMapper extends BaseMapper<Response> {}
```

**关键坑：`@Transactional` 与 `@DS` 不能混用**

- `@Transactional` 一开启事务，连接被绑定在主库 `response_db`
- 后续 `@DS("survey")` 想切数据源，但当前线程已有事务连接，**不会切换**
- 结果：在 `response_db` 查 `survey` 表，报 `Table 'response_db.survey' doesn't exist`

**正确写法：拆两个 Bean**

```
PublicResponseService（无 @Transactional）
  ├─ 读 survey_db（校验问卷、题目、选项）
  ├─ 读 response_db（查重）
  └─ 调 ResponseWriteService.write(...)
       └─ 有 @Transactional，只写 response_db
```

**核心：匿名答卷与防重**

答卷者不登录，用 `respondent_key`（前端 UUID，localStorage 持久化）标识身份。

| 层     | 实现                                                       | 作用             |
| ------ | ---------------------------------------------------------- | ---------------- |
| 应用层 | 提交前 `selectCount(surveyId, respondentKey)`              | 友好提示"已提交" |
| 数据库 | `uk_survey_respondent(survey_id, respondent_key)` 唯一索引 | 并发兜底         |

**唯一索引兜底**：应用层查重有竞态窗口（两个请求同时查到"无记录"），插入时唯一索引会抛 `DuplicateKeyException`，捕获后返回 40901。

**核心：回执码**

提交成功返回 16 位 `receipt_code`（32 字符集，去掉 `I/O/0/1`），用户可凭回执查询自己的提交。**不用登录态识别**，降低答卷门槛。

**核心：IP 限流**

Redis 固定窗口计数：

```java
String ipKey = "rl:submit:ip:" + clientIp;
if (!rateLimiter.tryAcquire(ipKey, submitPerHour, Duration.ofHours(1))) {
    throw new BusinessException(42901, "提交过于频繁");
}
```

**位置**：在查问卷之前——恶意刷 404 的请求也限流，避免数据库被打爆。

**核心：统计聚合**

| 题型               | 统计内容                                               |
| ------------------ | ------------------------------------------------------ |
| `RATING`           | 平均分 + 分值分布（`scoreDistribution`）               |
| `SINGLE` / `MULTI` | 选项分布（`optionDistribution`）；开启评分时还计算均分 |
| `TEXT` / `IMAGE`   | 文字答案列表（`textAnswers`）                          |

**关键：选择题参与评分**

选项带分值（`question_option.score`），单选题得选中项的分值，多选题得选中项分值之和。

```java
for (Long oid : ids) {
    optionDist.merge(optionLabelMap.get(oid), 1L, Long::sum);
    if (scoreEnabled) {
        Integer optScore = optionScoreMap.get(oid);
        if (optScore != null) thisScore += optScore;
    }
}
scores.add(thisScore);
avg = scores.stream().average().orElse(0);
```

**为什么应用层聚合而非 SQL GROUP BY**：数据量小（问卷通常几百份答卷），应用层逻辑更灵活，支持复杂的"选项 → 分值"映射。

#### 3.2.4 `file-service`（文件服务）

**作用**：

- 生成 MinIO 预签名上传 URL
- 登记附件元数据（`attachment_ref`）
- 生成预签名下载 URL

**数据库**：`response_db.attachment_ref`

| 字段          | 说明                               |
| ------------- | ---------------------------------- |
| `biz_type`    | `QUESTION` / `RESPONSE` / `SURVEY` |
| `biz_id`      | 业务主键（上传时可为空）           |
| `object_key`  | MinIO 对象键（**唯一索引**）       |
| `uploader_id` | 上传者                             |

**核心：预签名直传**

```
浏览器                      file-service              MinIO
  │  ① POST /api/file/presign  │                       │
  │ ──────────────────────────► │                       │
  │                             │  ② 生成预签名 URL      │
  │                             │ ────────────────────► │
  │  ③ 返回 objectKey + URL     │                       │
  │ ◄────────────────────────── │                       │
  │  ④ PUT 图片到 MinIO URL      │                       │
  │ ──────────────────────────────────────────────────► │
  │  ⑤ POST /api/file/confirm   │                       │
  │ ──────────────────────────► │  ⑥ 写 attachment_ref   │
```

**为什么直传**：

- 图片二进制**不经过业务服务**，不占 JVM 内存
- 大文件上传不阻塞业务线程
- 架构瓶颈转移到 MinIO（可水平扩展）

**核心：安全设计**

| 项                           | 实现                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| **objectKey 由服务端生成**   | `bizType/yyyy/MM/dd/uuid.ext`，前端不能控制，防路径穿越      |
| **MIME 白名单**              | 只允许 png/jpeg/gif/webp，防 XSS（HTML/SVG）                 |
| **大小上限 10MB**            | 前端 + 后端双重校验                                          |
| **预签名 URL 5 分钟**        | 短时效，泄露风险可控                                         |
| **`/api/file/url` 在白名单** | 答卷页无 JWT，需获取展示 URL；objectKey 是随机 UUID，不可枚举 |

**核心：`biz_id` 允许 NULL**

上传图片时业务 id 可能还不存在（新建题目未保存），所以 `biz_id` 允许 NULL。

**孤儿附件清理**（S6 待办）：定时任务清理 7 天前 `biz_id` 仍为 NULL 的附件。

### 3.3 AI 编排层

#### 3.3.1 `ai-orchestrator`（AI 编排服务）

**作用**：

- AI 生成题目草案
- AI 辅助评分（文本题、图片题、选择题）
- 调用审计（记录 `model_name`、`prompt_version`、`response_id`）

**数据库**：`response_db.ai_evaluation`（**只写审计表，不碰业务库**）

| 字段             | 说明                                    |
| ---------------- | --------------------------------------- |
| `response_id`    | 关联的答卷 id                           |
| `question_id`    | 关联的题目 id                           |
| `model_name`     | 模型名，如 `gpt-4o-mini`                |
| `prompt_version` | Prompt 版本                             |
| `rating`         | AI 评分 1-5                             |
| `reason`         | 评分理由                                |
| `confidence`     | 置信度 0-1                              |
| `status`         | `SUCCESS` / `FAILED` / `PENDING_REVIEW` |

**唯一索引**：`uk_response_question_model(response_id, question_id, model_name)`——同一份答卷同一题同一模型只有一条记录，重新评分时覆盖。

**核心：三条架构约束**

| 约束                  | 实现                                                         |
| --------------------- | ------------------------------------------------------------ |
| **AI 不碰业务库**     | 只读写 `ai_evaluation`，其他表只读                           |
| **AI 不覆盖用户数据** | 用户原始打分在 `response_answer.rating_value`，AI 结果在 `ai_evaluation.rating`，分表 |
| **AI 生成需人工确认** | 生成接口只返回草案，保存由用户手动触发                       |

**核心：AI 生成题目**

```
用户输入主题 → Prompt 模板 → ChatClient 调用 → 结构化输出（GeneratedSurvey）→ 前端填充 → 用户确认 → 保存
```

**关键**：`.entity(GeneratedSurvey.class)` 让 Spring AI 自动生成 JSON Schema 并反序列化，避免手动解析。

**Prompt 模板**（`resources/prompts/generate-survey.st`）：

- 明确角色："你是一位专业的问卷设计专家"
- 明确约束：题型范围、选项数量
- 明确输出：JSON Schema

**核心：AI 辅助评分**

文本题评分流程：

```
1. 拿题目 + 答案
2. Prompt：请对以下回答进行质量评分（1-5 分）
3. ChatClient 调用
4. 解析 rating/reason/confidence
5. 业务校验（rating 1-5，confidence 0-1）
6. 幂等写入 ai_evaluation
```

**关键坑 1：模型输出裸双引号**

模型会在 `reason` 里用未转义的英文双引号（`"reason": "回答仅为"无"..."`），导致 JSON 非法。

**解法**：

- System Prompt 明确禁止英文双引号，改用「」
- `.content()` 拿原始文本，手动解析
- 状态机修复裸双引号：

```java
if (c == '"') {
    if (!inString) { inString = true; }
    else {
        // 看后一个非空白字符，是 ,}]: 则是结束引号，否则是裸引号
        if (isEnd) { inString = false; } else { sb.append("\\\""); }
    }
}
```

**关键坑 2：重复评分触发唯一索引冲突**

同一 `responseId + questionId + modelName` 再次评分，`insert` 会报 `DuplicateKeyException`。

**解法：幂等落库**

```java
AiEvaluation existing = selectOne(responseId, questionId, modelName);
if (existing != null) {
    updateById(entity);       // 覆盖
} else {
    try { insert(entity); }
    catch (DuplicateKeyException e) {
        // 并发兜底：改为 update
    }
}
```

**关键坑 3：前端 15 秒超时**

Axios 全局 `timeout: 15000`，AI 调用通常 10-30 秒。

**解法**：

- `api/ai.ts` 给 AI 接口单独设置 `timeout: 60000`
- 后端 `RestClient` 的 `readTimeout` 调到 120 秒

**选择题 AI 评分**

选择题没有"文字答案"，但可以分析选项分布：

```
输入：题型、总答卷数、各选项人数和百分比
Prompt：请分析答卷者的倾向性、意见集中度
输出：rating/reason/confidence
```

**rating 的语义**：对选择题而言，`rating` 是"分布合理性"而非"某人得分"。前端 UI 明确标注"AI 生成，仅供参考"。

**AI 评分锚点**

当前实现取"该问卷第一条答卷的 id"作为 `responseId`。

**限制**：只对一份答卷评分，不是全量。

**S6 优化方向**：改为批量评分接口，返回该题所有答卷的 AI 均分。

- `meta.public: true` 的路由直接放行
- 其他路由检查 Pinia 的 `token`，无 token 跳 `/login?redirect=...`
- 已登录访问 `/login` 自动跳列表

#### 3.4.2 请求层（`utils/request.ts`）

**统一封装**：

| 层                       | 处理                                  |
| ------------------------ | ------------------------------------- |
| 请求拦截                 | 注入 `Authorization: Bearer ${token}` |
| 响应拦截（`code=0`）     | 返回 `body.data`（解包）              |
| 响应拦截（`code=40101`） | 清 token，跳登录                      |
| 响应拦截（HTTP 401）     | 同上                                  |
| 响应拦截（其他 `code`）  | `ElMessage.error`，reject             |

**关键**：`request` 实例解包了 `data`，所以页面里直接拿业务数据，不用 `.data.data`。

#### 3.4.3 编辑器状态（`stores/surveyDraft.ts`）

**核心数据结构**：

```typescript
interface QuestionDraft {
  uid: string              // 前端临时 id，用于 v-for key
  type: QuestionType
  title: string            // 纯文本摘要
  contentHtml: string | null
  imageKey: string | null
  required: boolean
  scoreEnabled: boolean
  scoreMin: number
  scoreMax: number
  options: OptionDraft[]   // 选项带 score
}
```

**为什么用前端 `uid`**：

后端整体覆盖式保存，`question.id` 每次重建都变化。前端用 `uid` 做 `v-for key`，避免拖拽和选中状态在保存前后丢失。

**`toSaveRequest` 剥离 `uid`**：提交给后端时去掉 `uid`，按数组顺序提交，`sortOrder` 由服务端赋值。

#### 3.4.4 组件

| 组件                   | 作用                                                         |
| ---------------------- | ------------------------------------------------------------ |
| `QuestionRenderer.vue` | 按题型渲染交互控件，**答卷页和预览页共用**（`readonly` prop 控制交互） |
| `QuestionEditor.vue`   | 题目编辑（题型切换、选项编辑、评分配置、题目图片）           |
| `RichEditor.vue`       | wangEditor 封装，支持插入图片                                |
| `AdminLayout.vue`      | 发布端布局                                                   |

**关键：`QuestionRenderer` 的 `v-if` 链条**

Vue 中 `v-if` / `v-else-if` / `v-else` **必须是相邻的兄弟元素**。如果在其中插入任何非条件元素，**链条断裂**，后续分支变成独立判断。

**反例**：

```vue
<el-input v-if="type === 'TEXT'" />
<div class="spacer"></div>           <!-- ❌ 打断链条 -->
<el-radio-group v-else-if="type === 'SINGLE'" />   <!-- 永远不会渲染 -->
```

**正确**：

```vue
<el-input v-if="type === 'TEXT'" />
<el-radio-group v-else-if="type === 'SINGLE'" />
<el-checkbox-group v-else-if="type === 'MULTI'" />
<div v-else-if="type === 'RATING'" />
<div v-else-if="type === 'IMAGE'" />
<el-alert v-else />                  <!-- 兜底 -->
```

## 四、数据模型设计

### 4.1 三库划分

| 库            | 表                                                           | 归属服务                                        |
| ------------- | ------------------------------------------------------------ | ----------------------------------------------- |
| `user_db`     | `user`                                                       | user-service                                    |
| `survey_db`   | `survey`、`question`、`question_option`                      | survey-service                                  |
| `response_db` | `response`、`response_answer`、`attachment_ref`、`ai_evaluation` | response-service、file-service、ai-orchestrator |

**为什么不用一个库**：

- 分库后每个服务的数据边界清晰，未来可独立分片
- 备份策略可分开（`response_db` 数据量增长快，`survey_db` 相对静态）
- 跨库读靠双数据源，跨库写几乎不存在

### 4.2 关键索引

| 表                | 索引                         | 作用                   |
| ----------------- | ---------------------------- | ---------------------- |
| `user`            | `uk_username`                | 登录唯一性             |
| `survey`          | `uk_share_code`              | 分享码唯一，允许 NULL  |
| `question`        | `idx_survey_version`         | 按版本取题目的高频查询 |
| `response`        | `uk_survey_respondent`       | **匿名防重核心**       |
| `response`        | `uk_receipt_code`            | 回执码唯一             |
| `response_answer` | `uk_response_question`       | 防同题重复写入         |
| `attachment_ref`  | `uk_object_key`              | 附件唯一               |
| `ai_evaluation`   | `uk_response_question_model` | **AI 评分幂等核心**    |

## 五、关键设计决策汇总

| 决策                               | 理由                                                | 代价                                          |
| ---------------------------------- | --------------------------------------------------- | --------------------------------------------- |
| **双数据源 vs Feign**              | response-service 需要跨库读，双数据源少一次网络调用 | `@DS` 与 `@Transactional` 不能混用，需拆 Bean |
| **快照机制**                       | 发布后编辑不影响已收集答卷                          | 存储翻倍（旧版本题目保留）                    |
| **整体覆盖式保存**                 | 逻辑简单，语义清晰                                  | `question.id` 每次重建，附件 `biz_id` 失效    |
| **复制为新草稿 vs 原地改 version** | 已发布 shareCode 不能变                             | 用户需手动复制                                |
| **预签名直传**                     | 大文件不占业务服务内存                              | 前端需裸 axios，不走项目 request 实例         |
| **`biz_id` 允许 NULL**             | 上传时业务 id 可能不存在                            | 需孤儿清理 Job                                |
| **AI 不覆盖用户数据**              | 用户打分是事实，AI 是建议                           | 结果页要展示两份数据                          |
| **AI 生成需人工确认**              | AI 输出不可靠                                       | 用户需手动保存                                |
| **幂等评分**                       | 支持重复评分                                        | 需先查后写，代码复杂度略增                    |
| **双层白名单**                     | Gateway + 服务层都校验                              | 改一处漏一处会 401                            |

## 六、关键场景数据流

### 6.1 发布者创建并发布问卷

```
1. 前端 → Gateway → user-service 登录 → 返回 JWT
2. 前端保存 JWT 到 localStorage
3. 前端 → Gateway → survey-service 创建问卷（DRAFT）
4. 编辑器：前端在本地维护 QuestionDraft[]（含 uid）
5. 点"保存草稿" → PUT /api/surveys/{id}
   → 后端：全量校验 → 删除旧题 → 重建 → 返回 QuestionView[]
6. 点"发布" → POST /api/surveys/{id}/publish
   → 后端：校验状态 → 生成 shareCode → 冻结 publishedVersion
   → 返回 shareUrl
```

### 6.2 答卷者匿名提交

```
1. 答卷者打开 /s/{shareCode}
2. 前端：读取或生成 respondent_key（localStorage）
3. 前端 → Gateway（白名单）→ response-service
   → GET /api/public/surveys/{shareCode}
   → 双数据源：读 survey_db（题目/选项）
4. 答卷者填写 → 提交
   → POST /api/public/responses
   → IP 限流（Redis）
   → 查重（response_db）
   → 读题目/选项（survey_db）
   → 逐题校验答案
   → 写 response + response_answer（response_db，独立事务）
   → 返回 receiptCode
5. 前端记录 markSubmitted(shareCode)
```

### 6.3 AI 辅助评分

```
1. 发布者在结果页点"AI 辅助评分"
2. 前端 → Gateway → ai-orchestrator
   → POST /api/ai/responses/{responseId}/evaluate
3. ai-orchestrator：
   → 拼接 Prompt（题干 + 答案 或 选项分布）
   → ChatClient 调用 OpenAI（60s 超时）
   → 拿原始文本 → 状态机清洗 → 解析
   → 业务校验（rating 1-5）
   → 幂等写入 ai_evaluation
   → 返回 AiScoreResult
4. 前端展示 rating/reason/confidence
5. 用户原始打分（response_answer.rating_value）不变
```

## 八、总结

系统的核心设计思想是：

1. **业务边界清晰**：按"故障模式"和"数据生命周期"拆分服务，而不是按数据库表拆
2. **AI 是辅助而非决策**：AI 输出写入独立审计表，需人工确认，不影响业务事实
3. **快照保证一致性**：发布时冻结版本，答卷者看到的永远是发布时的内容
4. **防重在数据库层兜底**：应用层查重提供友好提示，唯一索引保证并发安全
5. **图片不经过业务服务**：预签名直传 MinIO，业务服务只签发"票据"

这五条原则支撑了系统从 S1 到 S5 的稳定演进，也是后续 S6 部署上线的基础。
